مفاهیم وردپرس که تا اینجا کار کردیم

این صفحه مفاهیم CPT، WP_Query، OOP، تاکسونومی، tax_query، لوپ، هوک‌ها و APIهای وردپرس را با مثال واقعی صفحات برند (/brands/ و /brands/{slug}/) توضیح می‌دهد.

۱) نمای کلی معماری برند

CPT + تگ ووکامرس تمپلیت لایت

برند یک پست‌تایپ مستقل است. محصولات همچنان با product_tag مرتبط‌اند. صفحه تک‌برند محصولات را با tax_query می‌گیرد. فهرست برندها یک برگه وردپرس با تمپلیت قابل‌تعویض است.

برگه /brands/← CPT brand← product_tag← محصولات
ایده کلیدی: برند = صفحه محتوایی؛ تگ = پل داده برای محصولات.

۲) پست‌تایپ سفارشی (Custom Post Type)

CPT یعنی نوع محتوای جدید جدا از نوشته و برگه. ما brand را ثبت کردیم تا هر شرکت یک پست جدا با لوگو، چکیده، محتوا و URL خودش داشته باشد.

گزینه ثبتمعنیدر پروژه ما
publicقابل مشاهده در فرانتtrue
has_archiveآرشیو خودکار CPTfalse (به‌جایش برگه)
rewrite.slugپایه URL سینگلbrands
supportsفیلدهای ویرایشگرtitle, editor, thumbnail, excerpt
taxonomiesتاکسونومی‌های متصلproduct_cat, product_tag
query_varنام متغیر کوئریlk_brand (جلوگیری از تداخل)

۳) پیوند یکتا و ری‌رایت

وردپرس URLهای زیبا را با قوانین ری‌رایت به کوئری داخلی ترجمه می‌کند. سینگل برند: /brands/merck/ → پست‌تایپ brand با نام merck.

  • تغییر rewrite نیاز به Flush دارد (flush_rewrite_rules).
  • قوانین اضافه با add_rewrite_rule برای صفحه‌بندی سینگل امن‌تر شدند.
  • مسیر قدیمی /brand/... با ۳۰۱ به /brands/... می‌رود.

۴) برگه در برابر آرشیو CPT

آرشیو CPT

خودکار با has_archive. در ادیتور برگه قابل ویرایش نیست.

برگه + تمپلیت

در Pages ساخته می‌شود؛ عنوان/اسلاگ/تصویر شاخص قابل‌ویرایش؛ تمپلیت قابل‌تعویض.

ما has_archive = false گذاشتیم و فهرست را با برگه اسلاگ brands + تمپلیت Light brands template ساختیم.

۵) تمپلیت صفحه (Page Template)

تمپلیت یعنی فایل PHP که وردپرس برای رندر یک برگه استفاده می‌کند. در ادمین: برگه ← ویژگی‌ها ← قالب.

  • ثبت با فیلتر theme_page_templates
  • ذخیره در متا: _wp_page_template
  • ورود رندر: page-templates/light-brands.php → page-light-brands.php
  • خاموش کردن تمپلیت = برگشتن به قالب پیش‌فرض

برای سینگل برند هم تمپلیت لایت با template_include و template_redirect اجبار می‌شود تا Elementor/Jet نگیرند.

۶) تاکسونومی (Taxonomy)

تاکسونومی سیستم دسته‌بندی پست‌هاست. در ووکامرس: product_cat (دسته) و product_tag (برچسب/برند عملیاتی).

  • Term = یک مقدار داخل تاکسونومی (مثل تگ merck)
  • برند CPT می‌تواند همان تگ‌ها را داشته باشد تا رابطه معنایی حفظ شود
  • محصولات همچنان روی تگ می‌مانند؛ صفحه برند فقط از تگ برای کوئری استفاده می‌کند
چرا تاکسونومی برند جدا نساختیم؟ چون محصولات از قبل تگ داشتند؛ ساخت تاکسونومی موازی یعنی مهاجرت داده و دوباره‌کاری فیلترها.

۷) Tax Query — کوئری بر اساس تاکسونومی

tax_query آرگومان WP_Query است که می‌گوید: «فقط پست‌هایی را بیاور که این termها را دارند.»

جریان در سینگل برند

  1. پست برند merck لود می‌شود
  2. تگ اصلی پیدا می‌شود (ترجیح اسلاگ یکسان)
  3. کوئری محصول با tax_query روی همان تگ اجرا می‌شود
// مفهومی — از single-brand-light.php
$args = array(
  'post_type'      => 'product',
  'posts_per_page' => 12,
  'tax_query'      => array(
    array(
      'taxonomy'         => 'product_tag',
      'field'            => 'term_id',
      'terms'            => array( $term_id ),
      'include_children' => false,
    ),
  ),
);
$query = new WP_Query( $args );
کلیدتوضیح
taxonomyنام تاکسونومی هدف
fieldنوع شناسایی term: term_id / slug / name
termsآرایه termهای مجاز
include_childrenبرای سلسله‌مراتبی؛ تگ تخت است → معمولاً false
relationبین چند شرط: AND یا OR

اگر تگ پیدا نشود، به‌جای برگرداندن همه محصولات از post__in => array(0) استفاده می‌شود تا نتیجه خالی بماند.

۸) WP_Query — موتور پرس‌وجوی وردپرس

Query API

WP_Query کلاس اصلی برای واکشی پست‌ها از دیتابیس است. تقریباً هر لیست در وردپرس (آرشیو، جستجو، محصولات برند، کارت‌های صفحه شرکت‌ها) در نهایت به یک کوئری می‌رسد.

کوئری یعنی چه؟

کوئری (Query) یعنی یک درخواست ساخت‌یافته به دیتابیس: «کدام نوع پست؟ با چه شرطی؟ چند تا؟ به چه ترتیبی؟ کدام صفحه؟» وردپرس این درخواست را به SQL ترجمه می‌کند، نتیجه را می‌گیرد و داخل یک آبجکت WP_Query می‌گذارد تا تم بتواند روی آن لوپ بزند.

URL / $args→ WP_Query→ SQL→ WP_Post[]→ تمپلیت / Twig

چرخه زندگی یک درخواست صفحه

  1. مرورگر URL می‌زند (مثلاً /brands/merck/)
  2. Rewrite قانون را به query vars تبدیل می‌کند (post_type=brand, name=merck)
  3. وردپرس Main Query را می‌سازد و پست برند را پیدا می‌کند
  4. تمپلیت سینگل لود می‌شود
  5. داخل تمپلیت یک کوئری دوم برای محصولات همان برند اجرا می‌شود
  6. نتایج رندر می‌شوند (گرید محصول + صفحه‌بندی)

کوئری اصلی در برابر کوئری سفارشی

Main Query

کوئری‌ای که وردپرس از روی URL می‌سازد (مثلاً سینگل برند یا برگه /brands/). در global $wp_query است و با pre_get_posts قابل تغییر است. تمپلیت سلسله‌مراتب و تگ‌های شرطی معمولاً به همین کوئری نگاه می‌کنند.

Secondary / Custom Query

کوئری جدا که خودتان می‌سازید: new WP_Query( $args ) — مثل لیست محصولات داخل صفحه برند. روی URL اثر نمی‌گذارد؛ فقط داده اضافه برای همان صفحه می‌آورد.

اشتباه رایج: تغییر Main Query برای «لیست محصولات داخل صفحه برند» باعث می‌شود وردپرس فکر کند خود صفحه، آرشیو محصول است. برای همین محصولات را با کوئری دوم می‌گیریم.

ساختن کوئری: از آرگومان تا نتیجه

  1. آرایه $args را می‌نویسید (قوانین فیلتر)
  2. new WP_Query( $args ) یک نمونه (instance) می‌سازد
  3. داخل سازنده، کوئری اجرا می‌شود و $query->posts پر می‌شود
  4. با لوپ (have_posts / the_post) روی نتایج حرکت می‌کنید
  5. از found_posts و max_num_pages برای شمارش و pagination استفاده می‌کنید

آرگومان‌های پرکاربرد

آرگومانمعنیمثال در پروژه

post_statusوضعیت انتشارpublish
posts_per_pageتعداد در هر صفحه12 یا -1 (همه)

orderby / orderمرتب‌سازیکارت‌های برند: title / ASC

tax_queryفیلتر تاکسونومیمحصولات یک تگ برند
meta_queryفیلتر متای پستفیلترهای پیشرفته‌تر فروشگاه

// سینگل برند: کوئری سفارشی محصولات
$query = new WP_Query( array(
  'post_type'      => 'product',
  'post_status'    => 'publish',
  'posts_per_page' => 12,
  'paged'          => $paged,
  'tax_query'      => array( /* product_tag برند */ ),
) );

// صفحه شرکت‌ها: همه برندها
$posts = get_posts( array(
  'post_type'      => 'brand',
  'post_status'    => 'publish',
  'posts_per_page' => -1,
  'orderby'        => 'title',
  'order'          => 'ASC',
) );

صفحه‌بندی داخل کوئری

posts_per_page = 12 یعنی هر صفحه ۱۲ نتیجه. paged = 2 یعنی صفحه دوم. تعداد کل صفحات ≈ ceil( found_posts / posts_per_page ) و در $query->max_num_pages آماده است. URL سینگل برند برای صفحه ۲ چیزی شبیه /brands/merck/page/2/ است.

get_posts در برابر WP_Query

  • get_posts() لایه نازک روی WP_Query است و معمولاً آرایه پست برمی‌گرداند.
  • new WP_Query() آبجکت کامل می‌دهد: صفحه‌بندی، found_posts، max_num_pages، متدهای لوپ.
  • برای لیست ساده کارت‌ها get_posts کافی است؛ برای آرشیو محصول با pagination معمولاً WP_Query بهتر است.

خواص و متدهای مهم آبجکت کوئری

pre_get_posts — دست‌کاری قبل از اجرا

قبل از اینکه Main Query به دیتابیس برود، هوک pre_get_posts اجرا می‌شود. اینجا می‌توانید آرگومان‌ها را عوض کنید؛ مثلاً در آرشیو دسته/تگ محصول فقط post_type = product بماند تا پست‌های برند قاطی نشوند. 

public static function keep_product_tax_archives_on_products( WP_Query $query ): void {
  if ( is_admin() || ! $query->is_main_query() ) {
    return;
  }
  if ( ! $query->is_tax( array( 'product_cat', 'product_tag' ) ) ) {
    return;
  }
  $query->set( 'post_type', 'product' );
}

نکته: همیشه با $query->is_main_query() چک کنید تا کوئری‌های فرعی تم/ویجت خراب نشوند.

چند کوئری در یک صفحه — تصویر ذهنی برند

کوئریچه می‌پرسد؟نتیجه
Main URL /brands/merck/ کدام پست است؟ یک WP_Post از نوع brand
Custom #1 محصولات با تگ هم‌اسلاگ کدام‌اند؟ لیست product + صفحه‌بندی
(اختیاری) فیلترها همان محصولات با شرط اضافه کاربر همان کوئری محصول با tax_query/meta_query غنی‌شده

رابطه با SQL (بدون ترس)

شما معمولاً SQL خام نمی‌نویسید. WP_Query برای شما چیزی شبیه این می‌سازد: 

SELECT wp_posts.*
FROM wp_posts
INNER JOIN wp_term_relationships ON ...
WHERE post_type = 'product'
  AND post_status = 'publish'
  AND term_taxonomy_id IN ( /* id تگ merck */ )
LIMIT 12 OFFSET 0;

tax_query همان JOIN و شرط term است. paged=2 با OFFSET پیاده می‌شود. لایه پایین‌تر هسته $wpdb است؛ برای لیست پست‌ها همان WP_Query امن‌تر و خواناتر است.

در پروژه ما: کوئری اصلی = خود پست برند یا برگه فهرست؛ کوئری دوم = محصولات همان برند با tax_query. این جداسازی مهم است تا URL برند با لیست محصول قاطی نشود.

۹) برنامه‌نویسی شی‌گرا (OOP) در این پروژه

Class · Object · Method

کد برند را به‌جای توابع پراکنده، داخل کلاسها نوشتیم. OOP کمک می‌کند منطق مرتبط را کنار هم نگه داریم، هوک‌ها را منظم ثبت کنیم، و با نام‌های واضح از تداخل با افزونه‌ها جلوگیری کنیم.

مفاهیم پایه

مفهومتوضیح سادهمثال وردپرس / پروژه
Class (کلاس) قالب/نقشه یک مفهوم: چه داده‌هایی دارد و چه کارهایی می‌تواند بکند WP_Query، Hello_Elementor_Child_Brand_Cpt
Object / Instance یک نمونه واقعی ساخته‌شده از کلاس با new $query = new WP_Query( $args )
Property داده داخل آبجکت $query->found_posts، $query->posts
Method تابع متعلق به کلاس/آبجکت $query->have_posts()، $query->set()
static متد/خاصیت متعلق به خود کلاس؛ بدون new صدا زده می‌شود Brand_Cpt::init()، Custom_Brand_Single::is_enabled()
final class کلاس قابل ارث‌بری نیست (قفل طراحی) کلاس‌های تم ما اغلب final هستند

چرا کلاس‌های تم ما بیشتر static هستند؟

برای قابلیت‌هایی مثل «ثبت CPT» یا «اجبار تمپلیت»، معمولاً به یک نمونه با state طولانی نیاز نداریم. یک کلاس = یک ماژول. متدهای static مثل namespace مرتب برای توابع مرتبط‌اند: 

final class Hello_Elementor_Child_Brand_Cpt {
  public static function init(): void {
    add_action( 'init', array( __CLASS__, 'register_post_type' ), 99 );
    add_action( 'template_redirect', array( __CLASS__, 'redirect_tags_to_brand' ), 0 );
  }

  public static function register_post_type(): void { /* ... */ }
}

// بوت تم:
Hello_Elementor_Child_Brand_Cpt::init();

array( __CLASS__, 'register_post_type' ) یعنی: «وقتی هوک آتش شد، همین متد استاتیک کلاس را صدا بزن.» این همان اتصال OOP به Plugin API وردپرس است.

WP_Query خودش یک آبجکت است

وقتی می‌نویسید new WP_Query( $args ):

  1. یک instance جدید از کلاس ساخته می‌شود
  2. سازنده (constructor) آرگومان‌ها را می‌گیرد و کوئری را اجرا می‌کند
  3. نتیجه داخل propertyهایی مثل posts و found_posts می‌نشیند
  4. متدهایی مثل have_posts() روی همان instance کار می‌کنند
$query_a = new WP_Query( array( 'post_type' => 'brand' ) );
$query_b = new WP_Query( array( 'post_type' => 'product' ) );
// دو آبجکت مستقل؛ نتایج همدیگر را خراب نمی‌کنند

این دقیقاً فایده OOP است: چند کوئری همزمان، هر کدام state خودشان را دارند.

WP_Post هم آبجکت است

هر ردیف نتیجه معمولاً یک WP_Post است با propertyهایی مثل ID، post_title، post_name، post_content. توابع کمکی (get_permalink( $post )) روی همین آبجکت کار می‌کنند.

نقشه‌ی کلاس‌های برند در تم

کلاسمسئولیت (تک‌وظیفه‌ای)
Hello_Elementor_Child_Brand_Cptثبت CPT، rewrite، ریدایرکت تگ/URL قدیمی
Hello_Elementor_Child_Custom_Brand_Singleتمپلیت لایت سینگل، دارایی‌ها، بردکرامب
Hello_Elementor_Child_Light_Brands_Templateتمپلیت برگه فهرست شرکت‌ها و کارت‌ها

ایده طراحی: هر کلاس یک حوزه دارد (Separation of Concerns). هوک‌ها در init ثبت می‌شوند؛ منطق سنگین در متدهای جدا. WP_Query ابزار داده است؛ کلاس‌های تم orchestrator رفتار صفحه هستند.

مقایسه سریع: procedural در برابر OOP

سبک تابعی (procedural)

تابع‌های جدا در functions.php: lk_register_brand()، lk_enqueue_brand(). برای پروژه کوچک خوب است؛ با رشد کد نام‌ها قاطی و نگهداری سخت می‌شود.

سبک شی‌گرا (آنچه ما داریم)

هر قابلیت یک کلاس + init(). نام‌ها زیر namespace کلاس می‌مانند؛ هوک‌ها یکجا ثبت می‌شوند؛ مسئولیت‌ها جداست.

Encapsulation و سطح دسترسی

  • public — از بیرون قابل صدا زدن (هوک‌ها باید public باشند).
  • private — فقط داخل همان کلاس (مثلاً map_brand_card یا تشخیص اسلاگ از URL).
  • self::method() — صدا زدن متد دیگر همان کلاس.
  • __CLASS__ — نام کلاس فعلی؛ برای ثبت callable هوک مفید است.
// هوک باید متد public ببیند:
add_action( 'wp_enqueue_scripts', array( __CLASS__, 'enqueue_light_assets' ), 5 );

// منطق داخلی می‌تواند private بماند:
private static function map_brand_card( WP_Post $brand ): ?array { /* ... */ }

Type hint = قرارداد OOP با وردپرس

وقتی می‌نویسیم function keep...( WP_Query $query ) به PHP می‌گوییم: این پارامتر باید آبجکت از کلاس WP_Query باشد. همین‌طور WP_Post $brand در متدهای کارت برند. این هم خوانایی است هم خطای زودهنگام اگر چیز اشتباه پاس شود.

۱۰) لوپ (The Loop) و تگ‌های شرطی

The Loop

الگوی استاندارد وردپرس برای پیمایش نتایج کوئری: 

if ( $query->have_posts() ) {
  while ( $query->have_posts() ) {
    $query->the_post();
    // the_title(), get_the_ID(), get_permalink() ...
  }
  wp_reset_postdata(); // برگرداندن global $post به حالت قبل
}

بعد از لوپ سفارشی، wp_reset_postdata() مهم است تا قالب/هدر با پست اشتباه کار نکند.

تگ‌های شرطی (Conditional Tags)

توابعی که می‌گویند «الان چه نوع صفحه‌ای هستیم؟» و معمولاً روی کوئری اصلی کار می‌کنند:

تابعمعنیکاربرد ما
is_singular('brand')سینگل یک برندفعال‌سازی تمپلیت لایت برند
is_page()برگهصفحه فهرست شرکت‌ها
is_post_type_archive('brand')آرشیو CPTریدایرکت به برگه (آرشیو خاموش است)
is_product_tag()آرشیو تگ محصول۳۰۱ به سینگل برند
is_admin()پیشخوانجلوگیری از اجرای فرانت‌هوک‌ها در ادمین
wp_doing_ajax()درخواست AJAXخروج زودهنگام از بعضی چک‌ها

Query Vars

متغیرهایی مثل name، paged، post_type، یا سفارشی lk_brand که از URL/کوئری‌استرینگ خوانده می‌شوند (get_query_var('paged')).

۱۱) فیلدهای پست و توابع محتوا

هر پست یک آبجکت WP_Post است. فیلدهای اصلی که برای برند استفاده کردیم:

۱۲) Post Meta، Options و تمپلیت برگه

Post Meta

داده اضافه برای یک پست: get_post_meta / update_post_meta. مثلاً alt تصویر پیوست، یا فیلدهای ACF روی برند/تگ.

Options API

تنظیم سراسری سایت: get_option / update_option. ما فلگ flush ری‌رایت را اینجا نگه می‌داریم تا فقط یک‌بار اجرا شود.

Page template meta: برگه فهرست، مسیر تمپلیت را در _wp_page_template = page-templates/light-brands.php ذخیره می‌کند. با خواندن این متا می‌فهمیم کدام برگه «شرکت‌ها» است.

۱۳) تم فرزند، ثابت‌ها و بارگذاری کلاس‌ها

کار ما داخل child theme است (hello-elementor-child) تا آپدیت تم والد کد سفارشی را پاک نکند.

  • HELLO_ELEMENTOR_CHILD_PATH / URI — مسیر و آدرس فایل‌های تم
  • class-theme.php — require_once کلاس‌ها و فراخوانی ::init()
  • هر قابلیت (CPT، سینگل برند، تمپلیت برگه) کلاس جدا با متد init برای ثبت هوک‌ها
  • تمپلیت‌های PHP ورودی + ویوهای Twig برای HTML
functions / Theme::init→ load classes→ Class::init hooks→ request

۱۴) هوک‌ها (Hooks)

هوک نقطه اتصال تم/افزونه به هسته وردپرس است بدون ویرایش هسته. دو نوع اصلی دارد:

Action

در لحظه مشخص کاری انجام بده. مقدار برنمی‌گرداند. مثال: add_action('init', ...)

Filter

یک مقدار را بگیر، تغییر بده، برگردان. مثال: add_filter('body_class', ...)

اولویت (Priority)

عدد سوم در add_action / add_filter اولویت است. عدد کوچک‌تر زودتر اجرا می‌شود. PHP_INT_MAX یعنی «آخرین نفر باش و ببر».

هوکنوعکار در پروژه برند
initactionثبت CPT، تاکسونومی، rewrite
pre_get_postsactionاصلاح کوئری اصلی (آرشیو دسته فقط محصول)
template_redirectaction۳۰۱، اجبار تمپلیت لایت، قطع Elementor
template_includefilterانتخاب فایل PHP نهایی
woocommerce_get_breadcrumbfilterخانه → فروشگاه → شرکت‌ها → برند
wp_enqueue_scriptsactionلود/حذف CSS و JS
body_classfilterکلاس‌هایی مثل lk-light-brand
theme_page_templatesfilterاضافه کردن تمپلیت به لیست برگه
init→ parse request→ template_redirect→ enqueue→ render

۱۵) APIهای وردپرس مرتبط

در وردپرس «API» معمولاً یعنی مجموعه توابع و هوک‌های رسمی برای یک حوزه مشخص — نه لزوماً REST. مهم‌ترین‌هایی که در این پروژه لمس کردیم:

Plugin API (هوک‌ها)

همان add_action / add_filter / do_action / apply_filters. قلب توسعه تم و افزونه.

Rewrite API

add_rewrite_rule، flush_rewrite_rules، تنظیمات rewrite داخل register_post_type. مسئول URLهای /brands/....

HTTP / Redirect API

wp_safe_redirect( $url, 301 ) برای انتقال دائمی URLهای قدیمی به جدید. روی هوک template_redirect اجرا می‌شود.

Query API

WP_Query، get_posts، pre_get_posts، آرگومان‌هایی مثل tax_query و meta_query.

Template API / Hierarchy

template_include، single_template، get_page_template_slug، سلسله‌مراتب فایل‌های تم.

Options API

get_option / update_option برای فلگ یک‌باره flush مثل hello_elementor_child_brand_cpt_flush_v4.

REST API (زمینه)

با show_in_rest => true روی CPT، برند در Gutenberg/REST قابل دسترسی است. صفحات لایت ما عمدتاً با تمپلیت PHP/Timber رندر می‌شوند، نه کلاینت REST.

۱۶) Script/Style API — لود و حذف دارایی‌ها

وردپرس برای CSS/JS یک API رسمی دارد تا وابستگی‌ها، ترتیب و نسخه فایل‌ها کنترل شود. این همان بخشی است که در class-custom-brand-single.php می‌بینید.

توابع کلیدی

تابعنقش
wp_enqueue_styleصف‌بندی CSS برای چاپ در صفحه
wp_enqueue_scriptصف‌بندی JS (با وابستگی و footer)
wp_add_inline_styleCSS کوچک بعد از یک handle ثبت‌شده
wp_dequeue_style/scriptخارج کردن از صف چاپ
wp_deregister_style/scriptحذف ثبت کامل handle
wp_style_isبررسی اینکه استایل registered/enqueued هست یا نه
filemtimeنسخه‌گذاری فایل برای کش‌باستیگ

پارامترهای enqueue

wp_enqueue_style(
  $handle,   // نام یکتا مثل 'lk-light-product'
  $src,      // URL فایل
  $deps,     // آرایه handleهایی که باید قبلش لود شوند
  $ver,      // نسخه (اینجا filemtime یا ثابت تم)
);

چرا هم enqueue هم dequeue؟

  • enqueue: استایل/اسکریپت لایت خودمان را بیاور (کارت شاپ، تگ، دسته، تب‌ها).
  • dequeue: Elementor/Jet و دارایی‌های سنگین لیستینگ را بردار تا با تمپلیت لایت قاطی نشوند.
نکته اولویت: enqueue_light_assets روی اولویت ۵ لود می‌شود؛ dequeue_listing_assets روی ۱۰۰ تا بعد از ثبت افزونه‌ها حذف کند.

۱۷) پیاده‌روی روی کد انتخاب‌شده

بخش disable_jet_archive_template تا dequeue_listing_assets در سینگل برند:

الف) خاموش‌کردن تمپلیت Jet

public static function disable_jet_archive_template( $template_id ) {
  return self::is_brand_request() ? 0 : $template_id;
}

این یک فیلتر است. اگر درخواست صفحه برند باشد، به‌جای ID تمپلیت Jet عدد 0 برمی‌گرداند (= بدون تمپلیت سفارشی Jet). وگرنه مقدار قبلی دست‌نخورده می‌ماند.

ب) صف‌بندی دارایی‌های لایت

  1. اگر برند نیست → خروج زودهنگام (is_brand_request)
  2. لود فیلترهای آرشیو محصول در صورت وجود کلاس
  3. CSS کارت شاپ با وابستگی فونت وزیرمتن
  4. زنجیره وابستگی: فونت → فیلتر → کارت → light-product → tag → category
  5. wp_add_inline_style: متغیر ستون‌ها برای برند (--lk-lpt-cols:4)
  6. اسکریپت‌های ووکامرس (سبد) + کروم لایت + تب‌های مشخصات

ج) حذف دارایی‌های مزاحم

لیست handleهای Elementor / Jet / لیستینگ قدیمی با wp_dequeue_* و wp_deregister_* پاک می‌شود. سپس صف باقیمانده هم برای نام‌های شامل elementor / jet اسکن می‌شود.

الگوی دفاعی تم لایت: ۱) تمپلیت خودمان را اجبار کن → ۲) CSS/JS خودمان را enqueue کن → ۳) دارایی‌های رقیب را dequeue کن.

۱۸) ریدایرکت و سئو

  • /product-tag/{slug}/ → /brands/{slug}/ وقتی پست برند منتشر شده باشد
  • /brand/{slug}/ → /brands/{slug}/ (میراث URL قبلی)
  • کد وضعیت 301 = انتقال دائمی برای حفظ ارزش سئو
  • لینک‌های استریپ هوم‌پیج مستقیماً به URL جدید اشاره می‌کنند
